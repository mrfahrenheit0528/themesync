## Part 1 — Findings from this session (candidate material for Chapter 4)

### 1.1 GNN spatial predictions were being discarded by the CSP solver

**Symptom:** `mean_iou` (GNN-predicted position vs. CSP-resolved position) was
exactly `0.0000` across every evaluation trial, despite the GNN producing
non-trivial per-node predictions at inference time.

**Root cause** (`src/solvers/cassowary_engine.py`): for soft-constraint nodes,
the x-coordinate was *unconditionally* resolved via a center-alignment
constraint — the GNN's predicted x was never encoded as a constraint at all.
The y-coordinate was encoded only as a `weak`-strength suggestion, which was
consistently overridden by the `strong`-strength non-overlap stacking
constraint. Net effect: the GNN's output had no path by which it could
influence the final resolved layout.

**Fix:** nodes carrying a genuine GNN prediction (tracked via an explicit
`gnn_predicted` flag set by a new shared helper,
`LayoutGraphBuilder.apply_predictions()` — replacing 6 duplicated inline
loops across `evaluate.py`, `pipeline.py`, `candidate_generator.py`,
`experiment_runner.py`, `test_certificate_pipeline.py`, `test_id_pipeline.py`)
now have both x and y honored at `medium` constraint strength — enough to
take effect, since nothing else competes at that tier — while still yielding
to hard constraints, margins, and the non-overlap guarantee (`strong`/
`required`). Baseline (no-GNN) behavior is unchanged.

**Evidence:** `mean_iou` rose from `0.0000` to `0.1682` post-fix (3-trial
average, `evaluate.py`, academic-certificate payload).

### 1.2 GNN training objective didn't match the evaluation fitness function

**Symptom:** even after 1.1, GNN-guided layouts showed no quality advantage
over the no-GNN baseline (`C_total`: GNN 0.0779 vs. baseline 0.0626 on the
certificate payload).

**Root cause** (`src/models/train_gnn.py`): the evaluation fitness function
(`HeuristicEvaluator`, Formula 3.11) weights collision avoidance most heavily
(α=50 vs. β=2 alignment, δ=1.5 legibility), but the training loss
(`DifferentiableHeuristicLoss`) had **no collision term at all**, and computed
its boundary term using the model's own unsupervised, unconstrained
predicted width/height instead of each node's true fixed dimensions — the
network could trivially minimize loss by predicting degenerate sizes instead
of learning meaningful positions.

**Fix:** added a differentiable collision penalty (computed over each
layout's existing node-adjacency edges — avoids a dense pairwise cost matrix
over the batch); anchored the boundary term to true node dimensions
(`batch.x`, not model output); imported `HeuristicEvaluator`'s own α/β/δ
weights directly into the loss so the two objectives can't drift apart again.

### 1.3 Retraining surfaced a deeper bug: unnormalized input features

**Symptom:** retraining under the fix above produced a model that output
exactly `(0.0, 0.0)` for every single node — a fully collapsed, degenerate
prediction.

**Root cause** (`src/models/graph_builder.py`): raw pixel coordinates (up to
~750px in the CGL-Dataset training corpus) were fed into the GRU-based
message-passing network unnormalized, alongside 0–255 colour channels and a
0–1 saliency score. The scale mismatch dominated optimization.

**Fix:** node bbox and edge dx/dy features are now normalized to each
layout's own canvas dimensions (available per-sample in the training corpus
as `width`/`height`, previously unused; inference call sites now pass
`canvas_w`/`canvas_h` explicitly). Predictions are denormalized back to
pixels in `apply_predictions`. Retrained model produces varied,
per-node-differentiated predictions; training loss converges to a stable
~0.02–0.04 (previously monotonic collapse toward the degenerate constant).

### 1.4 AAPA candidate diversity collapses under GNN guidance (limitation, not fixed)

**Finding:** with GNN predictions now correctly honored (1.1), the 5
AAPA candidates generated by varying CSP margin/vertical-gap parameters
converge to near-identical resolved positions for interior singular nodes
when GNN guidance is active — confirmed by direct bbox comparison (8/11
nodes byte-identical across all 5 candidates). The same mechanism still
produces genuinely distinct layouts in baseline (no-GNN) mode.

**Diagnosis:** this is expected behavior under the Cassowary constraint
hierarchy, not a defect. Vertical-gap variation (12–26px across candidates)
acts as a *minimum*-spacing constraint, which is non-binding whenever the
GNN's own predicted inter-element spacing already exceeds it — which is
consistently the case, because the GNN has no explicit notion of
reading-order adjacency and produces gaps (400px+ between simple adjacent
elements) far in excess of any realistic vgap value.

**Decision (discussed and confirmed this session):** do **not** invent a new
"GNN-trust strength" diversity axis — it isn't grounded in the documented
AAPA methodology (which explicitly names margins/vertical-gaps/element
density as the varied parameters) and would itself require Chapter 3
revision to introduce honestly. Keeping margin/vgap as-is requires no code
change; recommended treatment is as a **Chapter 4 finding/limitation**,
tied to the GNN's lack of relative-ordering awareness as a future-work item.

### 1.5 Minor code-quality fixes bundled in

- `train_gnn.py`: hardcoded `cuda:2` device → `cuda` (would crash on <3 GPUs).
- `train_gnn.py`: `build_graph()` was being called twice per training sample
  (once in a list-comprehension filter, once in the body) — pure wasted
  compute, no correctness impact.

## Part 3 — Implementation of fixes 1–4

### 3.1 Alignment penalty → dynamic structural grid

`optimization_engine.py::calculate_alignment_penalty` now generates a
5-line grid from `canvas_w` and a `grid_margin` (default 50.0): left margin,
quarter, center, three-quarter, right margin. Each node's penalty is its
distance to the *nearest* of these, not just the center. `grid_margin` is a
fixed `HeuristicEvaluator` constant, independent of whatever margin a given
AAPA candidate's CSP resolution used (not plumbed per-candidate — would
require coupling `MetaheuristicStateExplorer`'s per-candidate margin into the
evaluator too, judged out of scope for this pass).

### 3.2 Legibility penalty → saliency-map cross-reference

- `VisionExtractor.calculate_saliency_map()` (new) bins SIFT keypoints into a
  20×20 heatmap over the image instead of one global density scalar.
- `TemplateIngestor.ingest()` now returns this heatmap as `saliency_map`
  alongside the existing scalar `saliency_weight`.
- `HeuristicEvaluator` accepts an optional `saliency_map`; `pipeline.py`
  threads it from Stage 0 (template ingestion) through to Stage 4 (ranking).
  Other entry points (`evaluate.py`, `experiment_runner.py`,
  `candidate_generator.py`'s self-test, both test files) don't supply a real
  image, so they get `saliency_map=None`.
- `calculate_legibility_penalty` is rewritten to scope to
  `structural_class == 'text_node'` nodes only (matching Formula 3.15's
  `TextNodes`), sampling the mean heatmap density under each node's bbox
  (scaled from canvas space to the source image's native pixel space), then
  **averaging across text nodes** — not summing, which is what Formula 3.15's
  literal pixel-sum would do. Averaging keeps this term on the same ~[0,1]
  scale as `P_align`/`P_space`/`P_collision`; summing made `P_legibility`
  swamp every other term (C_total jumped 0.078 → 7.95 in testing) including
  `P_collision`, contradicting the manuscript's own statement that α=50 makes
  collision the dominant term by design.
- When no real image is available, falls back to a flat density
  (`fallback_saliency=0.75`, matching the existing `_FALLBACK_SALIENCY`
  convention already used elsewhere for synthetic-fallback runs) rather than
  silently returning 0 for the (common) no-image case.
- The GNN's own `s_i` input feature (Formula 3.6) was **left untouched** —
  still the single global saliency scalar. Table 1 maps
  `extracted_saliency_weight` to *both* "Node Feature Aggregation" (implied
  by Formula 3.6's `s_i`, described in prose as a general "stylistic
  descriptor") and `p_i(legibility)` (explicitly, in Table 1's own row) — I
  only fixed the latter, since it's the one with a precise formula (3.15) the
  code demonstrably violated. Making `s_i` per-node too is a separate,
  smaller follow-up if you want full Table 1 fidelity — flag it if so.

### 3.3 K-Means → Elbow Method k-selection

`VisionExtractor._kmeans_cuda` now takes `k` as a parameter and returns WCSS
alongside centroids. New `_select_optimal_k_centroids` fits k ∈ [2, 6],
then `_find_elbow` picks the k whose WCSS point has the greatest
perpendicular distance from the chord connecting the curve's first and last
points (standard knee-detection heuristic). The grayscale/degenerate-image
fallback path (1D clustering on luminance only) still uses the fixed
`n_colors` — elbow selection wasn't extended there; flag if you want it too.
`k_min=2, k_max=6` are hardcoded — chosen to keep results compatible with
`aesthetic_renderer.py`'s existing `len(centroids) < 3` fallback (still
allows k=2, which triggers that fallback path gracefully rather than
crashing).

**Verification:** both test suites, `evaluate.py`, `candidate_generator.py`'s
self-test, `test_vertical_solver.py`, and a full `pipeline.py` run against a
real template image (`data/raw/sample_template.png`) all pass/complete
cleanly after these changes.

### 3.4 CNN aesthetic evaluator (gap 5) — built via heuristic distillation

Decision (confirmed with you): build now via distillation from the heuristic
fitness function (no human labels available yet); retrain later on MOS
scores once enough are collected — same architecture, swap the label source.

- **`src/models/aesthetic_cnn.py`** — `AestheticCNN` (4 conv blocks + global
  average pool + 2-layer FC regressor, ~small enough for a few-hundred-sample
  dataset without overfitting risk) and `rasterize_layout()`. No SVG
  rasterization library exists in `requirements.txt` (no cairosvg/svglib), so
  layouts are rasterized as colour-coded filled rectangles per node
  (text/image/repeating-group) rather than fully-styled renders — standard
  practice for layout-quality scorers in this literature (LayoutGAN,
  House-GAN, etc. train on exactly this kind of abstract rendering), and
  appropriate here since F_layout is itself a purely geometric function.
- **`src/data_preprocessing/generate_cnn_training_data.py`** — generates
  (image, label) pairs: random margin/vgap CSP configs per domain (same
  parametric space AAPA explores) + 40% additionally randomly jittered
  (deliberately allowed to overlap/go off-canvas) to widen the label
  distribution beyond "always near-optimal." Labels are `HeuristicEvaluator`'s
  `Total_Cost`. Generated 500 samples (250/domain); label range
  [1.16, 8.30], mean 1.77 — real spread, not degenerate.
- **`src/models/train_aesthetic_cnn.py`** — standard train/val split (85/15),
  MSE loss, Adam, saves best-val checkpoint to `themesync_cnn_v1.pth` along
  with the label mean/std (needed to denormalize predictions back to
  F_layout's scale). 40 epochs: val_mse 1.50 → 0.18 (normalized units).
- **Verification:** spot-checked predictions against ground truth on
  held-out configs — a jittered/degraded layout was correctly identified as
  much worse (heuristic 4.27 → predicted 4.02), and near-optimal
  configurations predicted near their true value (~1.12–1.19 vs true 1.19).
  One residual worth noting honestly: a "tight margins" config predicted 1.75
  vs. true 1.19 — because in synthetic-fallback mode (no real template
  image), the heuristic itself is largely insensitive to margin/vgap
  (flat saliency fallback, fixed evaluator-level alignment grid — same root
  cause as finding 1.4), so training labels contain a many-images-to-one-label
  mapping in that region that's inherently ambiguous to fit exactly. Not a
  CNN defect — a downstream consequence of an already-documented finding.
- **Integration:** deliberately **not** wired into `pipeline.py`'s live AAPA
  ranking — it stays a standalone, independently-invokable evaluator
  (`aesthetic_cnn.load_evaluator()` / `predict_score()`), so it doesn't
  change which candidate wins ranking or require another methodology
  discussion about what drives candidate selection. If you want it reported
  alongside `C_total` in `evaluate.py`/`experiment_runner.py`'s output
  tables, or wired into ranking itself, that's a follow-up ask.
- **Not done:** the grayscale-fallback K-Means path, the un-per-noded GNN
  `s_i` feature, MOS-based retraining — all flagged inline above as smaller
  follow-ups, not silently skipped.

### 3.5 Item 6 (YOLOv8 + OCR Semantic Layout Parsing) — in progress

Decision (confirmed with you): full build — fine-tune YOLOv8 on CGL-Dataset's
own annotation taxonomy rather than use generic pretrained COCO classes or a
lightweight heuristic-only remap.

**CGL-Dataset taxonomy** (enumerated directly from the dataset, not assumed):
exactly 4 categories — `logo` (id 1), `text` (id 2), `underlay` (id 3),
`embellishment` (id 4). Clean, well-defined, ideal for a 4-class detector.

**Mapping to ThemeSync's `structural_class`:** `text` → `text_node`;
`logo`/`underlay`/`embellishment` → `image_node` (the closest existing
category for a non-text graphic element — ThemeSync's schema is coarser than
CGL's). `repeating_group` (e.g. the 3 signature blocks in the certificate
domain) has **no YOLO-detectable equivalent** — it's a template-specific
structural pattern, not a generic visual category. Detected text boxes are
never auto-grouped into one; each becomes its own `text_node`. Flagged as a
known limitation, not silently handled.

**Data pitfall caught and fixed:** the first training attempt produced a
model with a perfectly normal, steadily decreasing training loss
(box/cls/dfl: 2.46/3.06/2.02 → 1.31/1.36/1.34 over 30 epochs) but exactly
`0/0/0/0` precision/recall/mAP on validation, every single epoch. Root
cause: I'd sourced the validation split from CGL-Dataset-v2's own `test`
split, assuming it had real annotations — direct inspection showed it
doesn't. Every `test`-split example carries a dummy placeholder annotation
(`bbox: [1, 2, 3, 4]`, `area: 12`) — CGL-Dataset-v2 evidently withholds real
test-set ground truth publicly (common for benchmark releases with a
held-out leaderboard). So every validation "match" was being scored against
meaningless placeholder boxes — the model may have been learning fine, the
*evaluation* was garbage. Fixed by sourcing both train and val from CGL's
real `train` split at disjoint index ranges (`train[0:3000]` /
`train[3000:3300]`) instead. Re-verified the corrected val labels have a
realistic 4-class distribution before retraining (previously: 100% class 0).
Flagging this because it's the kind of silent failure that's easy to miss —
a model can look like it "trained successfully" (clean loss curve, no
errors, weights file saved) while its reported metrics are meaningless.

**Built:**
- `src/data_preprocessing/prepare_yolo_dataset.py` — exports a subset of
  CGL-Dataset (reusing the same HF cache as GNN training) into YOLO's
  expected `images/`+`labels/`+`data.yaml` layout, converting `[x,y,w,h]`
  pixel annotations to YOLO's normalized `cx,cy,w,h` format. Ran with 3000
  train / 300 val samples (both from CGL's `train` split — see pitfall
  above) — 0 skipped (clean conversion).
- `src/models/train_yolo_extractor.py` — fine-tunes a pretrained `yolov8n.pt`
  base via the `ultralytics` API (already a pinned dependency —
  `requirements.txt` had it unused, now actually used). 30 epochs, imgsz 640.
- `src/data_preprocessing/layout_extractor.py` — inference wrapper:
  `LayoutExtractor.extract(image_path)` runs the fine-tuned detector, sorts
  detections into reading order (logo first, then top-to-bottom by y), maps
  each to a `structural_class`, and for `text_node` detections crops the
  region and runs Tesseract OCR (installed via conda-forge into
  `themesync_env` — wasn't present on the system at all until this session)
  to extract literal text (`node['ocr_text']`). Output is a node list with
  the same schema contract as `NodeInstantiator.instantiate_payload()`
  (`node_id`, `semantic_category`, `structural_class`, `spatial_hierarchy`,
  `bbox`, `constraint_type`), so it's a drop-in alternative input to the rest
  of the pipeline (GNN → CSP → AAPA), not a parallel schema.

**Training status:** complete (30 epochs, yolov8n base, 3000 train / 300 val,
correct — non-placeholder — validation split). Final validation:

Solid first-pass result for logo/text/underlay (the three classes that

**CRITICAL finding — domain mismatch on ThemeSync's actual target images.**
Ran `LayoutExtractor.extract()` against 3 real template images in
`data/raw/` (`sample_template.png`, `YOUR_TEMPLATE.png`, `YOUR_TEMPLATE2.jpg`).
At the default confidence threshold (0.25): **zero detections** on 2 of 3;
one weak logo detection (conf 0.46) on the third. Lowered the threshold to
0.01 to check whether the model was seeing *nothing* or just *not confident
enough* — it's the latter: `sample_template.png` produces 78 candidate boxes,
but the highest confidence among them is 0.11; `YOUR_TEMPLATE.png` produces
5 candidates topping out at 0.035. Both far below any usable threshold.

Root cause: this isn't a bug, it's a genuine train/inference domain gap. The
model generalizes fine *within* CGL-Dataset's own domain (mAP50=0.539 on its
own held-out images — real-world advertising/e-commerce posters: product
photography, dense marketing graphics).

**Clarified with the group lead (2026-09-10), two rounds of correction:**
first pass here wrongly assumed the 3 test files represented "certificates/
ID cards"; second pass (while scoping the annotation batch) noted they're
actually CSPC SSC event posters and concluded they were the *wrong* test
images entirely. Neither is right. The group lead clarified the actual
system design: a "master layout" in ThemeSync is **any generic branded
design** a user uploads (poster, banner, letterhead) — YOLO parses it only
to extract a visual *theme* (colors, logo style, decorative motifs), which
then gets synced onto a certificate/ID layout generated separately via the
existing JSON schema payload (`dynamic_instantiation.py`). YOLO never
processes a certificate/ID image directly — those are a structurally
different, already-working path. So `YOUR_TEMPLATE.png`/`YOUR_TEMPLATE2.jpg`
(CSPC SSC event posters "La Serata"/"YUGTO 2026") **are exactly the right
genre of test image** after all — the domain gap is real, just correctly
characterized as *CGL's photographic/e-commerce ad imagery vs. ThemeSync's
actual master-layout uploads (stylized, illustrated event-poster/branding
graphics)* — not "posters vs. certificates" as either earlier pass assumed.
This also resolves the open "replace vs. run alongside" integration
question below: it's "alongside" by design — YOLO/OCR and the JSON schema
payload serve two different concerns (master-layout theme extraction vs.
certificate/ID structural generation), not two competing implementations of
the same thing.

This is the *same underlying issue* already flagged for the GNN back in
Part 1, finding 1.2/1.3 — CGL-Dataset is out-of-domain relative to
ThemeSync's actual use case — just now confirmed for YOLO too, and more
visibly, since detection confidence is a much more direct signal of "does
this model recognize what it's looking at" than a spatial-prediction loss
value is. Worth stating as one unified, cross-cutting limitation rather than
two separate ones: **both of ThemeSync's learned components share a training
corpus that doesn't represent its actual deployment domain.**

This means the "full build" as currently trained is **not yet usable on
ThemeSync's real master-layout uploads** — it works, but only on
CGL-Dataset's own kind of imagery. Fixing this properly needs either (a) a
small set of *real* master-layout images (event posters/branding assets —
see `notes/annotation_guidelines.md`), hand-annotated with logo/text/
underlay boxes, to fine-tune further on top of the CGL base (transfer
learning from a reasonable starting point, rather than from scratch), or
(b) accepting this as a documented limitation and future-work item
alongside the GNN's own domain-mismatch finding. Option (a) is now in
progress — see 3.6.

**Integration (deliberately not done yet):** `layout_extractor.py` is
standalone, not wired into `pipeline.py`'s default flow yet. As clarified
above, the design intent is for it to run *alongside* the JSON-schema-payload
path, not replace it — YOLO/OCR handles master-layout theme extraction,
the schema payload still handles certificate/ID structural generation and
per-record dynamic content. Actually wiring the two together is still
pending, but the *design question* itself is resolved.

### 3.9 Two dashboard-surfaced bugs fixed (2026-09-15): output aspect ratio + palette role assignment

Building the Figure 2 dashboard (section 3.8 continued — see
`src/dashboard/app.py`) and actually driving real uploads through it
surfaced two real bugs that unit tests hadn't caught, because both only
show up when a real master-layout image is combined with a target format
whose aspect ratio differs from that image's own.

**Bug 1 — output canvas silently ignored the selected target format.**
`_derive_canvas()` in `pipeline.py` prioritized the uploaded master-layout
image's native pixel dimensions over the payload's own
`target_aspect_ratio`. Uploading a square (2048×2048) poster and selecting
"Identification Card (2:3)" produced a **1:1 square ID**, not the intended
638×1014 portrait — the image's incidental size silently overrode the
selected domain format. Root cause: this priority ordering predates the
"master layout ≠ the literal cert/ID template" clarification (section 3.5)
and was never revisited once that changed — back when the uploaded image
*was* assumed to be the literal template, using its native size as the
canvas made sense; it stopped making sense the moment "master layout"
became "a generic poster used only to extract a theme." Fixed by removing
the native-image-size branch entirely; canvas dimensions now come from
explicit CLI args or the payload's own domain default, never the source
image. Verified: re-ran the ID pipeline against the same square poster —
canvas correctly resolved to 638×1014.

**Bug 2 — palette derivation assumed a fixed 3 centroids; Elbow Method
(section 3.3) can return 2–6.** The previous session's fix to
`_palette_from_centroids()` (using all 3 K-Means centroids instead of
silently dropping the 3rd) assumed centroids are always length-3. But
`VisionExtractor._select_optimal_k_centroids()` already implements the
Elbow Method from section 3.3, so real images return anywhere from 2 to 6
centroids depending on perceptual complexity — a fixed-3 assumption would
truncate extra centroids (discarding real extracted colour data again, the
same class of bug as before) or fall through to the entirely-hardcoded
default palette whenever an image happened to elbow-select only 2.
Generalized the role-assignment logic to handle any count in `[2, 6]`:
darkest centroid → primary, lightest → background, most chromatic
(furthest from neutral grey in LAB a*/b*) of whatever remains → accent; if
only 2 centroids exist (no true "middle" one), accent is instead a
punchier same-hue tint of primary rather than an unrelated hardcoded gold.
Verified directly against synthetic centroid lists of length 1, 2, 3, and
5 (all four produced sensible, non-crashing palettes; k=5's test
deliberately embedded one high-chroma and two low-chroma middle
centroids, confirming the high-chroma one was correctly selected as
accent) — actual images tested this session all happened to elbow-select
k=3, so the 2/4/5/6 paths are verified via direct unit-level calls, not
yet observed end-to-end on a real image.

Both fixes verified against the real "CSPC SSC — Assistants & Committee
Directors" poster (uploaded via the dashboard); both existing test suites
still pass with no regressions.

### 3.11 Wired Stage 0b's detected logo aspect ratio into `lock_aspect_ratio` (2026-09-15) — Figure 2's "Affine scaling"

Figure 2's UI mockup (p. 51) lists "Affine scaling: Unlocked" under the
SIFT/SURF Keypoints readout, and both real payload files

### 3.16 Empty bottom space fixed with a vertical-balance soft constraint, checked against the manuscript first (2026-09-28)

**Problem (§3.14–3.15):** in baseline (no-GNN) mode both formats left the
bottom 20–25% of the canvas empty. Cassowary stacked the nodes with
inequalities only (`top >= prev.bottom + gap`, `top >= margin`) and
nothing pinned the stack vertically, so the solver parked it on the top
margin.

**Manuscript check before touching code (the user's request):**

| Option | Where | Verdict |
|---|---|---|
| **A. Soft "equal top/bottom margins" constraint** | Cassowary | ✅ **Aligned.** p.39: "Soft Constraints: Standard design rules (e.g., default margins)… are assigned finite weights… minimizing the total error" (Formula 3.5); p.38: margins/padding as linear relations (Formula 3.3). Balanced vertical margins is a standard design rule of exactly that kind. Hard constraints (manual nudges, Formula 3.4) still override it, so HITL is untouched. No change to Formulas 3.11–3.15, the Appendix B schema, or the AAPA parameters. Also matches Optimization Theory's "geometric balance, whitespace distribution" (p.61) and MOS's "negative space aligns with professional composition standards" (p.58). |
| B. Stretch the vertical gaps to fill the page | Cassowary | ⚠️ Conflicts with AAPA, whose candidates deliberately vary the vertical gap (margins / vertical gaps / element density); stretching overrides that parameter. |
| C. Schema field to anchor the role/signature rows to the bottom | payload | ❌ Changes Appendix B's schema (currently an exact match to the code). |
| D. New "vertical balance" penalty term | Formula 3.11 | ❌ A fifth term in a four-term formula: a Chapter 3 rewrite. |

**Implemented A** (`cassowary_engine.py`, step 4):
`first.top + last.bottom == canvas_h` at `strong`, the same tier as the
margin rules. "Last" is the signature row when there is one.

- **Why above the GNN:** the GNN's position hints are `medium`, so the GNN
  still decides the arrangement *within* the stack, and the balance rule
  decides where the stack sits on the canvas.
- **First attempt stretched rather than moved the stack.** The gaps were
  only lower-bounded, so the solver satisfied the balance equation by
  opening a big hole under the certificate logo. I added a `weak`
  preference for each gap to equal the candidate's vgap. Being weak, it
  is only a tie-breaker (the GNN's `medium` positions still win), but it
  keeps the stack compact so it moves as a block.

**Verified:**
- YUGTO event ID and certificate, with and without the GNN (Cairo
  renders). All four are balanced top and bottom.
- `test_vertical_solver.py`: top gap 157.25 px = bottom gap 157.25 px.
- All tests pass.
- The GNN certificate still shows its own ~300 px logo gap (§1.4). That is
  GNN behavior, deliberately left alone.

**Finding for Chapter 4: the fitness function can't see this problem.**
The certificate test's C_total stayed at exactly GNN 1.2029 / base 1.1876
after the stack moved, because in synthetic mode every penalty is
invariant to vertical translation:
- P_align measures x only (Formula 3.13 as implemented);
- P_whitespace is a global area ratio (Formula 3.14, position-blind by
  definition);
- collision is zero;
- legibility is flat without a real saliency map.

So Formula 3.14 cannot distinguish a balanced layout from a top-heavy
one. That is a concrete, documentable reason why the MOS step (Phase 4)
is needed on top of the fitness function, which is exactly what the
manuscript argues on p.58 and p.62.

**AAPA side effect:** the margin parameter now affects the vertical
position only when the content overflows, so in baseline mode candidates
differ mainly by vgap. This slightly narrows candidate diversity, a
limitation already noted in §1.4.

### 3.22 GNN v2: the train/inference mismatch, and retraining (2026-09-28)

**What the user saw:** certificates with a ~200 px gap under the logo.
Measured on 6 posters, the first gap was 184–227 px on every GNN-guided
certificate while every other gap had collapsed to 6 px.

**Cause: v1 was never learning a layout.**
- **Mismatched input:** training fed each CGL layout's *true* positions
  as input. At inference Stage 1 handed every node (0, 0), an input it
  never saw in training.
- **Wrong target:** the loss rewarded only "centred, in bounds, no
  overlap", so nothing taught vertical order or spacing.
- **How the solver amplified it:** GNN positions are `medium`
  preferences, and the stack's gap was a solver variable with a 6 px
  floor. The solver shrank every gap to 6 px to pack the text near the
  GNN's (similar) predicted y's. The logo kept its own predicted y near
  the top, which left the hole.

**Fix (`src/models/train_gnn.py`, `graph_builder.naive_stack`):**
- **Same start in training and inference:** a *naive stack* (elements
  centred, stacked in reading order, uniform gap, stack centred
  vertically). Inference stacks in `spatial_hierarchy` order. The naive
  stack is also exactly what the CSP builds in baseline mode, so the GNN's
  contribution is precisely its learned departure from the baseline.
- **Target:** CGL-Dataset V2's real positions (Smooth-L1), plus a
  relational term on consecutive offsets (spacing and alignment
  structure), plus the fitness function's collision and in-bounds terms
  (weight 0.1) as regularisers.
- **Elements:** CGL logos and text only (58,011 layouts with ≥2 such
  elements). Underlays and embellishments are decoration, placed by the
  renderer (§3.23).
- **Validation split:** CGL's own test split has no annotations
  (placeholder boxes), so a seeded 5% of train (2,900 layouts) is held
  out.

**Held-out results** (`src/evaluation/gnn_heldout_eval.py` →
`results/gnn_heldout_eval.json`; fractions of the canvas):

| Model | Position MAE | Gap MAE | Order kept |
|---|---|---|---|
| v1 as deployed (0,0 start) | 0.210 | 0.349 | 47.1% |
| Naive stack (no model = baseline start) | 0.175 | 0.077 | 100% |
| v2, positions only (ablation) | 0.118 | 0.101 | 99.8% |
| **v2, positions + relations (default)** | **0.121** | **0.074** | **99.9%** |

v1 was worse than no model at all, and its 47% order rate is chance. v2
cuts position error 43% and gap error 79% relative to v1, and beats the
naive stack on both. The positions-only ablation places elements slightly
better but spaces them 31% worse than naive; spacing is what a stacked
certificate/ID depends on, so the relational model is the default.
Weights: `themesync_gnn_v2.pth` (default); `themesync_gnn_v2_posonly.pth`
(ablation); v1 kept for the record. Training logs: `results/gnn_v2/`.

**Solver changes (`cassowary_engine.py`):**
- **Minimum gap:** the candidate's vertical rhythm is a `strong` minimum
  gap (was `medium`), so the GNN can add space but never squeeze.
- **Maximum gap:** any one gap is capped at 10% of the canvas height
  (`strong`), so no prediction can open a hole.
- **Centre axis:** all stacked nodes share the centre axis at `strong`
  (every one of the 18 sample IDs is centred). The GNN's `medium`
  preference is now y only: it decides the vertical rhythm.

**Thesis implications:**
- Chapter 3 (pp.40–41) describes the architecture but not the training
  objective (revision list 3.13).
- Chapter 4 has a clean before/after (the table above).

### 3.23 Projecting the master's look: background, motifs, title artwork (2026-09-28)

**What the user saw:** "the generated IDs and certificates all look the
same, only differ in color."

**Cause:**
- The master reached the output only through its K-Means palette and
  logos.
- Every output was the same flat card with the same centred stack.
- The Legibility Penalty (Formula 3.15) scored text against the
  *stretched master poster*, a background the output never showed.

**The manuscript already implies more:**
- p.38 builds the saliency map from "the inpainted background layer".
- Figure 1(b) shows CGL's inpainted backgrounds.
- Figure 3's candidates carry the master's ornaments and lettering.

The group's 18 real event IDs all reuse their pubmat's artwork. The user
approved (2026-09-28) projecting background, motifs and title artwork,
lifting their earlier deferral.

**Stage 0c — `src/data_preprocessing/stylistic_markers.py`:**
- **Text-free background:** the poster's central area is rebuilt from its
  border by harmonic (Laplace) interpolation at 64 px.
  - YOLO misses big titles on unseen posters (HALUBILO, ORSEM), so
    inpainting only detected boxes left readable ghost titles.
  - OpenCV TELEA inpainting of large areas smears and leaves X-shaped
    seams.
  - The border fill keeps each backdrop's colours and light (sky over
    grass, magenta rays, dark space) with no text at all.
- **Motifs:** YOLO embellishment detections cut out with their
  surroundings cleared.
  - They are kept only if they separate cleanly: ≥50% of the outer ring
    cleared, 10–85% of the crop cleared.
  - Anything that is a logo, the title, or larger than 20% of the poster
    is excluded.
  - Motifs are ranked by confidence × SIFT keypoint density (the element's
    stylistic descriptor).
- **Title artwork:**
  - YOLO's line boxes are first merged into title groups (vertically
    adjacent, horizontally overlapping, comparable line heights). SIKLAB's
    title came as "SIKLAB / CSPC INTRAMURALS" plus a separate "2025", and
    a small tagline is kept out of a big title.
  - The largest title-sized group that separates cleanly is cut out.
  - A crop edge that still runs into artwork grows the box.
- **Human-in-the-loop:** motif ticks, a title-artwork toggle or upload,
  and logo picks on the Figure 2 page.

**Rendering (`decor.py`, `aesthetic_renderer.py`):**
- **Layers:** text-free background (cover-scaled) → certificate panel
  (near-white with the poster's hue, 6.5% inset, so the poster art frames
  it) with a double border → the event's title artwork as an 8% watermark
  on the panel → motifs → content.
- **Motifs:** placed in corners and along the sides, bleeding 18% off the
  edge. Right-hand ones are mirrored. They are shrunk, then dropped,
  rather than allowed to cover content.
- **Event ID:** the title artwork replaces the typed title when present.
- **Text colour:** picked against what is actually underneath (WCAG
  4.5:1). White with a soft shadow is used on dark art. The role band uses
  the poster's accent colour, deepened to 4.5:1 with white.
- **Typography:** Figure 2's user-injected font weight and base size B,
  collected but ignored until now, drive a type scale. Certificate title
  1.1 B, name 1.0 B, body text 0.36 B, date/ID 0.3 B, each capped by its
  box.
- **Certificate text boxes grew:** title 10% of the height, name 8.5%,
  citation 9%. The old 40 px title floated in an empty page.

**Scoring:**
- **Candidates:** each varies margin × vertical rhythm × motif
  arrangement (6 arrangements).
- **Legibility:** each candidate is scored against *its own* composed
  background's SIFT saliency map, which makes Formula 3.15 truthful.
- **Motifs in the fitness terms:**
  - Alignment and whitespace leave motifs out: they are placed off-grid
    and bleed off the page on purpose.
  - Collision ignores motif–motif overlap but counts a motif over
    content.
  - Motif boxes aren't clamped onto the canvas for overlap tests.

**Refinements after reviewing all 15 posters (2026-09-29):**
- **Motif filters:**
  - Small marks in the footer band are dropped (a Facebook "f" had become
    a HALUBILO 2025 motif).
  - Strips and slivers (aspect outside 0.3–3.3: a game health bar, side
    panels) are dropped.
  - Scattered fragments (less than 25% of the trimmed box visible) are
    dropped.
  - Anything showing a human face is dropped. ULAYAW's photo collage of
    real students had been cut as a "motif". Face detection uses OpenCV's
    YuNet model, bundled at `assets/models/` with its MIT licence, since
    OpenCV 5 no longer ships the Haar cascade classifier.
- **Title growth:**
  - A crop grows sideways while the raw poster shows lettering just
    outside its left or right end. This is needed because the background
    clearing erases letters that touch the crop border.
  - Vertical growth only follows visible content: an edge test pulled
    taglines and neighbouring art into titles.
  - Title art is now whole on 12 of 13 posters where it is found.
    SEARCH SSC 2025 keeps white letters on a near-white sky that the
    clearing still thins.
- **Per-poster override for Phase 4:** a `title_artwork` column in
  `manifest.csv` ("no" types the title), with a checkbox on the Phase 4
  page next to the preview.

**Known limits:**
- A title YOLO misses entirely (HALUBILO 2026) is typed, not cut.
- Motifs on busy art don't always separate, and are dropped.
- ORSEM's title artwork carries a patch of its glow.
- The automatic logo pick is still wrong on Mr and Ms CSPC (a red orb)
  and finds nothing on ULAYAW (a drawn badge) — both fixed with the
  Phase 4 page's logo picker (§3.21).

### 3.25 Weak detection on master layouts: model size and resolution first, labels second (2026-09-29)

**The user's question:** "the system weakly detects the logos and other
stuff from the master layout, is it because on how we annotated the
dataset?"

**Answer: partly the labels, mostly the model and its input size.**
- **Model and resolution.** v3 was YOLOv8n (3 M parameters) run at 640 px.
  Poster logos are small, often under 3% of the image. At 640 px a logo row
  is a few dozen pixels high.
- **Labels, two problems:**
  - 60 boxes cover more than half their poster (e.g., `underlay` 100% on
    ARKI SEARCH and CELAKBO, `embellishment` 75% on BU). They teach "the
    whole poster is an object".
  - `embellishment` holds both 2% sparkles and 40% mascots, two things the
    model can't learn as one rule.

**Experiment (v4):**
- **Model:** YOLOv8s from COCO, whole network, at 1024 px.
- **Training:** 120 epochs (patience 25), batch 8, seed 0.
- **Data:** a copy of the 124-image batch with the 60 over-half boxes
  deleted (`data/processed/yolo_master_v4/`, images symlinked).

Both models are scored on the same cleaned validation labels
(`results/yolo_v4_experiment.json`):

| | mAP50 | logo | text | underlay | embellishment |
|---|---|---|---|---|---|
| v3 (YOLOv8n, 640, original labels) | 0.363 | 0.620 | 0.584 | 0.037 | 0.212 |
| v4 (YOLOv8s, 1024, cleaned labels) | **0.454** | **0.818** | **0.682** | 0.115 | 0.201 |
| recall v3 → v4 | | 0.551 → 0.757 | 0.554 → 0.672 | 0.024 → 0.098 | 0.165 → 0.182 |

- **How to read it:** logos and text improved most, which is the
  capacity/resolution fix. Embellishment didn't move, which is the
  class-definition problem, and no model size fixes that.
- **Confound:** v4 changed size, resolution, initialisation and labels at
  once. The v5 re-annotation, trained with v4's exact recipe, isolates the
  labels' share.
- **v4 is the default** (`pipeline.DEFAULT_YOLO_WEIGHTS`, `themesync_yolo_v4.pt`).

**Inference changes (`layout_extractor.py`):**
- It predicts at the checkpoint's own training size (1024 for v4). Before,
  it always used 640.
- Title-sized text (≥ 5% of the image) is kept down to confidence 0.15. Big
  stylised titles score low, and false positives that large are rare.
- Class names come from the checkpoint (`model.names`), so a 5-class v5
  needs no code change. An unknown class maps to `image_node`.

**Logo row (`pipeline._select_logo_row`), rewritten:**
- Drop tiny footer icons.
- De-duplicate overlapping boxes.
- Cluster the logos into rows: centres within half the taller height,
  height ratio ≤ 1.8.
- Prefer a top-band row (≤ 25% of the height) with ≥ 2 logos, then a
  bottom-band row, then the middle. Otherwise take the single best logo.

On the 15 unseen Phase 4 posters the automatic row is now right on
**15 of 15** (7 of 15 with v3 and the old top-20% rule, §3.21).

**Fixing the labels (the user chose a re-annotation):**
- **`notes/annotation_guidelines.md` v2:**
  - a fifth class, `illustration`, for characters, mascots, emblems and
    objects;
  - `embellishment` restricted to small accents;
  - no box over half the poster;
  - photographs of people left unboxed;
  - the Roboflow steps (same split, no resize).
- **`finetune_yolo_master_layout.py`:**
  - `--check_only` lists per-class counts, class ids outside `names`
    (training refuses them) and over-half boxes (warned);
  - `--data` and `--seed` are new;
  - the v5 command uses v4's recipe.
- **Stage 0c (`stylistic_markers.MOTIF_CLASSES`)** takes motifs from
  `illustration` first (weight 1.0, up to 35% of the poster), then
  `embellishment` (0.6, up to 20%). With a 4-class model nothing changes
  (checked on SIKLAB, YUGTO 2025 and ORSEM: same motifs).
- `pipeline.DEFAULT_YOLO_WEIGHTS` prefers `themesync_yolo_v5.pt` once it

### 3.26 The GNN reads the master's structure (v3), registered to the master's anchors (2026-09-29)

**The user's observation:** "the gnn effect on the layouts is
insignificant."

**Why that was true:**
- v2 saw only the target's own boxes (sizes, palette, saliency). It started
  from the same naive stack for every master, so it learned one
  "CGL-looking" rhythm and applied it everywhere: a fixed 4–6% shift per
  poster.
- Nothing about the master's composition reached it. Table 1 maps an
  ingested element's `bbox [x, y]` to the GNN's initial feature encoding,
  but the implementation never passed the master's positions in (§3.11's
  boundary).

**Structure mapping (`src/models/structure_mapping.py`):**
- `master_structure()` reads four roles from Stage 0b's detections:
  - the logo row, if it sits above the title;
  - the organisation header: the text group between the logos and the
    title;
  - the title: the merged title group (§3.23);
  - the details: the first text group below the title, footer excluded.
- `anchors_for()` pins each target node with the same role to that centre.
- **Certificates anchor only the logo and header.** A poster's title and
  details positions don't transfer to a certificate's composition:
  anchoring them opened a 254 px hole in the art-column archetype.
- `graph_builder.structure_start()` places the unmapped nodes between the
  anchors in reading order.

**v3 training (`train_gnn.py --starts naive,structure`, `themesync_gnn_v3.pth`):**
- Each CGL layout is used twice:
  - from the naive stack, the no-master case;
  - from a distorted version of its own structure, as a cross-format
    mapping would deliver it: rescaled 0.75–1.25 and shifted ±8%
    vertically, jittered (σ 2.5% vertical, 3% horizontal), with up to half
    the elements unmapped.
- 60 epochs over 110,222 graphs; the best epoch is 55.
- Same loss as v2: positions, consecutive offsets, and the collision /
  in-bounds regularisers.

**Solver:** when the positions carry the master's composition, vertical
balance drops from `strong` to `weak` and a single gap may reach 30% of the
height. So a title placed low on the page, with room above for the hero,
survives the solve.

**Held-out CGL layouts (2,900, `results/gnn_heldout_eval.json`),**
fractions of the canvas:

| input → model | position error | gap error | order kept | overlap |
|---|---|---|---|---|
| naive stack, no model | 0.1750 | 0.0766 | 1.000 | 0.0000 |
| naive → v2 | 0.1207 | 0.0741 | 0.999 | 0.0000 |
| naive → v3 | 0.1212 | 0.0739 | 0.999 | 0.0000 |
| structure start, no model (mapping only) | 0.0503 | 0.0517 | 0.981 | 0.0044 |
| structure → v2 | 0.0961 | 0.0969 | 0.924 | 0.0037 |
| **structure → v3** | **0.0364** | **0.0411** | 0.971 | **0.0005** |

- With a structure to start from, v3 cuts the mapping's position error by
  28%, its gap error by 20% and its overlap by 89%.
- v2, never trained on such a start, makes it worse.
- Without a master, v3 is as good as v2.

**Found in evaluation, and fixed: v3 moved the master's own anchors.**
- **On real posters:** the first battery run had v3's structure error above
  the mapping's on several certificates (EDUKWELA: mapping 0.000, GNN
  0.078).
  - v3 was trained only on distorted starts, so it always "corrects".
  - On a real master the anchors aren't noise; they are the composition
    being transferred.
  - That run's palettes weren't seeded (§3.29), so its numbers aren't
    reported.
- **The clean test:** held-out layouts with **exact** anchors (real
  centres, up to half the elements unmapped). Vertical-centre error, as a
  fraction of the height (`exact_anchors` in the same JSON):

| | anchored elements | unmapped elements |
|---|---|---|
| mapping only (interpolation) | 0.0000 | 0.0812 |
| v3, raw | 0.0264 | 0.0843 |
| **v3, registered** | **0.0000** | **0.0746** |
| v2, registered | 0.0000 | 0.1088 |

- **Reading it:**
  - Raw v3 pulls correct anchors off by 2.6% of the height, and places the
    unmapped elements no better than interpolation.
  - **Registered to the anchors** (`graph_builder.register_to_anchors`), it
    keeps them exactly and places the unmapped elements 8% better than
    interpolation.
  - v2, registered, is worse than interpolation: v3's structure training is
    what earns the gain.
- **What Stage 2 does now:**
  - The mapped nodes keep the master's positions.
  - Each unmapped node goes between its neighbouring anchors in proportion
    to where the GNN put it.
  - In short, the mapping transfers the composition, and the GNN infers
    where the target's other elements go.
- **The solver respects the same order.**
  - An anchored node's position is held at `ANCHOR`
    (`cassowary_engine.py`), ten times `medium` and still below `strong`.
    So when not everything fits, the GNN's inferred nodes give way before
    the master's composition, and the design rules still win over both.
  - Found on EDUKWELA's certificate. Registration had put the logo row
    exactly, but the GNN's tight spacing under it made the solver trade the
    two `medium` preferences, and the logo moved up 3% of the height. With
    `ANCHOR` it stays and the text below moves.
  - The flag travels with the guided nodes, so the designer's re-solves
    (Figure 3) keep it too.

**Phase 3 battery (15 unseen posters × 2 formats × 3 conditions,
`results/experiment_log.json`):**

Run `20260929_103736`: YOLO v4, GNN v3 registered, seeded palettes.
Structure error is a fraction of the height (lower = closer to the
master); C_total is Formula 3.11.

| | GNN-guided | mapping only | baseline |
|---|---|---|---|
| **Certificates** — structure error, mean of 6 candidates | 0.113 (median 0.098) | 0.113 | 0.147 (median 0.133) |
| Certificates — C_total (winner) | 0.0015 | 0.0015 | 0.0017 |
| **Event IDs** — structure error, mean of 6 candidates | 0.067 (median 0.047) | 0.067 | 0.137 (median 0.115) |
| Event IDs — C_total (winner) | 0.1426 | 0.1420 | 0.1402 |
| Event IDs — P_legibility | 0.0029 | 0.0025 | 0.0013 |

**Structure error** (new in `experiment_runner.py`):
- It is how far the output's anchored elements sit vertically from their
  counterparts on the master, as a fraction of the height.
- It is reported for the winner and averaged over all six candidates. On
  certificates the candidates often tie on C_total, so the winner alone
  mostly reflects the ranking's tie-break.
- It measures what Formula 3.11 can't: whether the output keeps the
  master's composition.
- With registration, GNN and mapping share their anchored positions, so
  this metric separates structure from no structure. The GNN's own
  contribution, the unmapped elements, shows in the exact-anchor table
  above and is for Phase 4 to judge.

**Reading the battery:**
- **The master's structure now reaches the output, measurably.**
  - The GNN-guided output is closer to the master than the baseline on
    **15 of 15 event IDs**, at half the distance.
  - It is closer on **13 of 15 certificates**. The other two (MMCSPC,
    ORSEM) have no logo row or header above the title, and those are the
    only roles a certificate takes.
- **Formula 3.11 doesn't reward it:**
  - Certificates tie on 14 of 15.
  - On event IDs the baseline scores slightly better (GNN lower on 5,
    equal on 4, higher on 6), through legibility. Following a poster's
    composition puts text where the poster had its artwork, and the
    text-free background keeps that artwork, so the area is busier.
  - Nothing in the fitness function encodes "keeps the master's
    composition". That is the MOS's "visual hierarchy preservation" and
    "brand consistency", i.e. Phase 4.
- **GNN vs. mapping only:**
  - They share the winner, fitness and anchor positions on 29 of 30 runs.
  - The unmapped elements (name, role, the certificate's lower block) end
    up in different places on 8 of 30 runs: 3 certificates and 5 IDs, by
    up to 7.5% of the height (mean 0.6%).
  - Both formats are tall stacks with little vertical slack. Once the
    anchors are placed, Cassowary's `strong` rules leave the unmapped
    elements few choices.
  - So in this pipeline the GNN's contribution is small and bounded by
    design. Its advantage over interpolation is measured on held-out data
    (the exact-anchor table), not in the fitness scores.
  - Not tuned away: loosening the design rules to make the GNN "matter
    more" would bias the comparison.
- **Outlier: ULAYAW.** Its only logo is a badge in the middle of the
  poster, just above a low title. A certificate or ID can't put its
  leading logo row 60% of the way down with the rest of the stack still
  fitting below, so every condition scores about 0.32–0.42. That's a real
  limit of role mapping when the master's order conflicts with the
  target's, and it's why the medians are given too.
- **A trade-off the expert will see (ORSEM, event ID):** GNN and mapping
  reproduce the master's structure exactly (error 0.000) but score 0.164
  and 0.155 against the baseline's 0.138.

### 3.29 Stage 0's colour clustering was unseeded, so identical runs differed (2026-09-29)

**How it was found:** the battery's three conditions picked different
winners on ALAPS, even though two of them run identical code there.
- A quick test of two sessions agreed: K-Means often converges to the same
  clusters from different starts.
- Within one battery run, though, ALAPS's "Baseline Init" state scored
  0.0041 in two sessions and 0.0007 in the third. That state is the same
  unguided solve in every condition.

**Cause:** `vision_extraction._kmeans_cuda` (Formula 3.1) drew its initial
centroids with an unseeded `torch.randperm`. So a poster's palette could
come out different on every run, and so could the elbow-chosen k. That
changed:
- the panel and text colours;
- the Legibility Penalty;
- the winning candidate.

The grayscale path was already seeded (scikit-learn,
`random_state=42`).

**Fix:**
- Seeded initialisations.
- Each k keeps the best of 5, like the grayscale path's `n_init`.
- Cluster means are one one-hot matrix product instead of a per-cluster
  loop. That is faster (about 1.5 s per poster), and it avoids atomic
  scatter-adds, whose summation order varies on a GPU.
- Checked: repeated extraction gives identical centroids, and ALAPS's
  palette is unchanged from the loop version.

**Consequences:**
- Every result before this fix carries some palette noise, including the
  earlier batteries, the stale Phase 4 packet and the candidate sheets.
- The Phase 3 numbers in §3.26 come from the first run after it.
- The Phase 4 set has to be regenerated anyway (it predates §3.23–3.27).

### 3.33 Calibrating Formula 3.11's weights (2026-10-08, revision item 3.25)

**Why:** p.43 says α–δ were "empirically calibrated during Phase 3
testing"; p.52 says they were "iteratively calibrated" until the scores
"consistently align with strict architectural constraints and human-centric
design rules." The weights (α 50, β 2, γ 1, δ 1.5) had been set by hand,
from p.43's rule that α is the highest. The calibration should have come
before the Phase 4 packets (2026-10-07). The experts won't re-score, so it
was run as an analysis, and the deployed weights stay whatever it finds.

**Method (`src/evaluation/weight_calibration.py`, criteria fixed before
the run):**
- **Test set:** the Phase 3 battery, i.e. the 16 Phase 4 posters × 2
  formats × GNN/baseline = 64 runs, generated as the packet generated them.
  The weights only rank the six candidates, so each run's candidates are
  generated once and re-ranked under any weights. No expert rating is used.
- **A, constraints first (p.43):** the chosen layout must have no overlap
  and nothing off the canvas (p.56) wherever an option allows it, and α
  must stay the highest weight.
- **B, design rules (p.52):** from the deployed weights, each round tries
  one weight × 0.25, 0.5, 2 or 4. A change is kept only if the chosen
  layouts get better on average on alignment, whitespace or legibility
  and worse on none. It stops when no change qualifies.
- "Chosen" is what the system outputs: the fittest candidate of the layout
  type the master calls for (item 3.23). The plain ranking (lowest C_total
  of all six) is reported too.

**Result (`results/weight_calibration.json`):**
- **Reproduced:** all 64 runs' penalties, and all 64 choices match the
  pipeline and the Phase 4 key.
- **Criterion A holds**, trivially: none of the 384 candidates overlaps or
  leaves the canvas (Cassowary prevents it), so α's value never decides
  anything on this battery.
- **Criterion B: the loop keeps no change**, for both the deployed choice
  and the plain ranking. The deployed weights count as calibrated.
- **Robust:** halving or doubling any one weight changes at most **1 of the
  64 rated layouts** (KAINANG_PAMILYA certificate, GNN: F → B). At × 0.25
  or × 4, still at most 1. Only dropping a term entirely (× 0) changes
  more: whitespace 11, legibility 5.
- **Why the weights matter so little:**
  - alignment is near zero on every candidate (max 5 × 10⁻⁷), so β never
    decides;
  - 16 runs' layout type has only one candidate;
  - of the 48 runs with two candidates of the type, 22 are exact ties at 4
    decimals (generation order decides), and the median gap is 0.0002.
  - So the choices come down to whitespace against legibility, and
    Formula 3.11 barely separates the two candidates of a type (as §3.31
    found across types).

**For the thesis:** Chapter 3's wording can stay. Chapter 4 should say the
weights were set by p.43's priority rule and then confirmed by this
calibration, and give the robustness figure. It was run on 2026-10-08,
after the Phase 4 layouts were generated and before any rating was
analysed. Don't write that it came before the packets.
