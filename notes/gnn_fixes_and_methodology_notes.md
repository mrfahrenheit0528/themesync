## Part 1 — Findings from this session (candidate material for Chapter 4)

### 1.1 GNN spatial predictions were being discarded by the CSP solver

**Symptom:** `mean_iou` (GNN-predicted position vs. CSP-resolved position) was
exactly `0.0000` across every evaluation trial, despite the GNN producing
non-trivial per-node predictions at inference time.

**Root cause** (`src/solvers/cassowary_engine.py`): for soft-constraint nodes,
the x-coordinate was *unconditionally* resolved via a center-alignment
constraint — the GNN's predicted x was never encoded as a constraint at all.
The y-coordinate was encoded only as a `weak`-strength suggestion, which was
consistently overridden by the `strong`-strength non-overlap stacking
constraint. Net effect: the GNN's output had no path by which it could
influence the final resolved layout.

**Fix:** nodes carrying a genuine GNN prediction (tracked via an explicit
`gnn_predicted` flag set by a new shared helper,
`LayoutGraphBuilder.apply_predictions()` — replacing 6 duplicated inline
loops across `evaluate.py`, `pipeline.py`, `candidate_generator.py`,
`experiment_runner.py`, `test_certificate_pipeline.py`, `test_id_pipeline.py`)
now have both x and y honored at `medium` constraint strength — enough to
take effect, since nothing else competes at that tier — while still yielding
to hard constraints, margins, and the non-overlap guarantee (`strong`/
`required`). Baseline (no-GNN) behavior is unchanged.

**Evidence:** `mean_iou` rose from `0.0000` to `0.1682` post-fix (3-trial
average, `evaluate.py`, academic-certificate payload).

### 1.2 GNN training objective didn't match the evaluation fitness function

**Symptom:** even after 1.1, GNN-guided layouts showed no quality advantage
over the no-GNN baseline (`C_total`: GNN 0.0779 vs. baseline 0.0626 on the
certificate payload).

**Root cause** (`src/models/train_gnn.py`): the evaluation fitness function
(`HeuristicEvaluator`, Formula 3.11) weights collision avoidance most heavily
(α=50 vs. β=2 alignment, δ=1.5 legibility), but the training loss
(`DifferentiableHeuristicLoss`) had **no collision term at all**, and computed
its boundary term using the model's own unsupervised, unconstrained
predicted width/height instead of each node's true fixed dimensions — the
network could trivially minimize loss by predicting degenerate sizes instead
of learning meaningful positions.

**Fix:** added a differentiable collision penalty (computed over each
layout's existing node-adjacency edges — avoids a dense pairwise cost matrix
over the batch); anchored the boundary term to true node dimensions
(`batch.x`, not model output); imported `HeuristicEvaluator`'s own α/β/δ
weights directly into the loss so the two objectives can't drift apart again.

### 1.3 Retraining surfaced a deeper bug: unnormalized input features

**Symptom:** retraining under the fix above produced a model that output
exactly `(0.0, 0.0)` for every single node — a fully collapsed, degenerate
prediction.

**Root cause** (`src/models/graph_builder.py`): raw pixel coordinates (up to
~750px in the CGL-Dataset training corpus) were fed into the GRU-based
message-passing network unnormalized, alongside 0–255 colour channels and a
0–1 saliency score. The scale mismatch dominated optimization.

**Fix:** node bbox and edge dx/dy features are now normalized to each
layout's own canvas dimensions (available per-sample in the training corpus
as `width`/`height`, previously unused; inference call sites now pass
`canvas_w`/`canvas_h` explicitly). Predictions are denormalized back to
pixels in `apply_predictions`. Retrained model produces varied,
per-node-differentiated predictions; training loss converges to a stable
~0.02–0.04 (previously monotonic collapse toward the degenerate constant).

### 1.4 AAPA candidate diversity collapses under GNN guidance (limitation, not fixed)

**Finding:** with GNN predictions now correctly honored (1.1), the 5
AAPA candidates generated by varying CSP margin/vertical-gap parameters
converge to near-identical resolved positions for interior singular nodes
when GNN guidance is active — confirmed by direct bbox comparison (8/11
nodes byte-identical across all 5 candidates). The same mechanism still
produces genuinely distinct layouts in baseline (no-GNN) mode.

**Diagnosis:** this is expected behavior under the Cassowary constraint
hierarchy, not a defect. Vertical-gap variation (12–26px across candidates)
acts as a *minimum*-spacing constraint, which is non-binding whenever the
GNN's own predicted inter-element spacing already exceeds it — which is
consistently the case, because the GNN has no explicit notion of
reading-order adjacency and produces gaps (400px+ between simple adjacent
elements) far in excess of any realistic vgap value.

**Decision (discussed and confirmed this session):** do **not** invent a new
"GNN-trust strength" diversity axis — it isn't grounded in the documented
AAPA methodology (which explicitly names margins/vertical-gaps/element
density as the varied parameters) and would itself require Chapter 3
revision to introduce honestly. Keeping margin/vgap as-is requires no code
change; recommended treatment is as a **Chapter 4 finding/limitation**,
tied to the GNN's lack of relative-ordering awareness as a future-work item.

### 1.5 Minor code-quality fixes bundled in

- `train_gnn.py`: hardcoded `cuda:2` device → `cuda` (would crash on <3 GPUs).
- `train_gnn.py`: `build_graph()` was being called twice per training sample
  (once in a list-comprehension filter, once in the body) — pure wasted
  compute, no correctness impact.

## Part 3 — Implementation of fixes 1–4

### 3.1 Alignment penalty → dynamic structural grid

`optimization_engine.py::calculate_alignment_penalty` now generates a
5-line grid from `canvas_w` and a `grid_margin` (default 50.0): left margin,
quarter, center, three-quarter, right margin. Each node's penalty is its
distance to the *nearest* of these, not just the center. `grid_margin` is a
fixed `HeuristicEvaluator` constant, independent of whatever margin a given
AAPA candidate's CSP resolution used (not plumbed per-candidate — would
require coupling `MetaheuristicStateExplorer`'s per-candidate margin into the
evaluator too, judged out of scope for this pass).

### 3.2 Legibility penalty → saliency-map cross-reference

- `VisionExtractor.calculate_saliency_map()` (new) bins SIFT keypoints into a
  20×20 heatmap over the image instead of one global density scalar.
- `TemplateIngestor.ingest()` now returns this heatmap as `saliency_map`
  alongside the existing scalar `saliency_weight`.
- `HeuristicEvaluator` accepts an optional `saliency_map`; `pipeline.py`
  threads it from Stage 0 (template ingestion) through to Stage 4 (ranking).
  Other entry points (`evaluate.py`, `experiment_runner.py`,
  `candidate_generator.py`'s self-test, both test files) don't supply a real
  image, so they get `saliency_map=None`.
- `calculate_legibility_penalty` is rewritten to scope to
  `structural_class == 'text_node'` nodes only (matching Formula 3.15's
  `TextNodes`), sampling the mean heatmap density under each node's bbox
  (scaled from canvas space to the source image's native pixel space), then
  **averaging across text nodes** — not summing, which is what Formula 3.15's
  literal pixel-sum would do. Averaging keeps this term on the same ~[0,1]
  scale as `P_align`/`P_space`/`P_collision`; summing made `P_legibility`
  swamp every other term (C_total jumped 0.078 → 7.95 in testing) including
  `P_collision`, contradicting the manuscript's own statement that α=50 makes
  collision the dominant term by design.
- When no real image is available, falls back to a flat density
  (`fallback_saliency=0.75`, matching the existing `_FALLBACK_SALIENCY`
  convention already used elsewhere for synthetic-fallback runs) rather than
  silently returning 0 for the (common) no-image case.
- The GNN's own `s_i` input feature (Formula 3.6) was **left untouched** —
  still the single global saliency scalar. Table 1 maps
  `extracted_saliency_weight` to *both* "Node Feature Aggregation" (implied
  by Formula 3.6's `s_i`, described in prose as a general "stylistic
  descriptor") and `p_i(legibility)` (explicitly, in Table 1's own row) — I
  only fixed the latter, since it's the one with a precise formula (3.15) the
  code demonstrably violated. Making `s_i` per-node too is a separate,
  smaller follow-up if you want full Table 1 fidelity — flag it if so.

### 3.3 K-Means → Elbow Method k-selection

`VisionExtractor._kmeans_cuda` now takes `k` as a parameter and returns WCSS
alongside centroids. New `_select_optimal_k_centroids` fits k ∈ [2, 6],
then `_find_elbow` picks the k whose WCSS point has the greatest
perpendicular distance from the chord connecting the curve's first and last
points (standard knee-detection heuristic). The grayscale/degenerate-image
fallback path (1D clustering on luminance only) still uses the fixed
`n_colors` — elbow selection wasn't extended there; flag if you want it too.
`k_min=2, k_max=6` are hardcoded — chosen to keep results compatible with
`aesthetic_renderer.py`'s existing `len(centroids) < 3` fallback (still
allows k=2, which triggers that fallback path gracefully rather than
crashing).

**Verification:** both test suites, `evaluate.py`, `candidate_generator.py`'s
self-test, `test_vertical_solver.py`, and a full `pipeline.py` run against a
real template image (`data/raw/sample_template.png`) all pass/complete
cleanly after these changes.

### 3.4 CNN aesthetic evaluator (gap 5) — built via heuristic distillation

Decision (confirmed with you): build now via distillation from the heuristic
fitness function (no human labels available yet); retrain later on MOS
scores once enough are collected — same architecture, swap the label source.

- **`src/models/aesthetic_cnn.py`** — `AestheticCNN` (4 conv blocks + global
  average pool + 2-layer FC regressor, ~small enough for a few-hundred-sample
  dataset without overfitting risk) and `rasterize_layout()`. No SVG
  rasterization library exists in `requirements.txt` (no cairosvg/svglib), so
  layouts are rasterized as colour-coded filled rectangles per node
  (text/image/repeating-group) rather than fully-styled renders — standard
  practice for layout-quality scorers in this literature (LayoutGAN,
  House-GAN, etc. train on exactly this kind of abstract rendering), and
  appropriate here since F_layout is itself a purely geometric function.
- **`src/data_preprocessing/generate_cnn_training_data.py`** — generates
  (image, label) pairs: random margin/vgap CSP configs per domain (same
  parametric space AAPA explores) + 40% additionally randomly jittered
  (deliberately allowed to overlap/go off-canvas) to widen the label
  distribution beyond "always near-optimal." Labels are `HeuristicEvaluator`'s
  `Total_Cost`. Generated 500 samples (250/domain); label range
  [1.16, 8.30], mean 1.77 — real spread, not degenerate.
- **`src/models/train_aesthetic_cnn.py`** — standard train/val split (85/15),
  MSE loss, Adam, saves best-val checkpoint to `themesync_cnn_v1.pth` along
  with the label mean/std (needed to denormalize predictions back to
  F_layout's scale). 40 epochs: val_mse 1.50 → 0.18 (normalized units).
- **Verification:** spot-checked predictions against ground truth on
  held-out configs — a jittered/degraded layout was correctly identified as
  much worse (heuristic 4.27 → predicted 4.02), and near-optimal
  configurations predicted near their true value (~1.12–1.19 vs true 1.19).
  One residual worth noting honestly: a "tight margins" config predicted 1.75
  vs. true 1.19 — because in synthetic-fallback mode (no real template
  image), the heuristic itself is largely insensitive to margin/vgap
  (flat saliency fallback, fixed evaluator-level alignment grid — same root
  cause as finding 1.4), so training labels contain a many-images-to-one-label
  mapping in that region that's inherently ambiguous to fit exactly. Not a
  CNN defect — a downstream consequence of an already-documented finding.
- **Integration:** deliberately **not** wired into `pipeline.py`'s live AAPA
  ranking — it stays a standalone, independently-invokable evaluator
  (`aesthetic_cnn.load_evaluator()` / `predict_score()`), so it doesn't
  change which candidate wins ranking or require another methodology
  discussion about what drives candidate selection. If you want it reported
  alongside `C_total` in `evaluate.py`/`experiment_runner.py`'s output
  tables, or wired into ranking itself, that's a follow-up ask.
- **Not done:** the grayscale-fallback K-Means path, the un-per-noded GNN
  `s_i` feature, MOS-based retraining — all flagged inline above as smaller
  follow-ups, not silently skipped.

### 3.5 Item 6 (YOLOv8 + OCR Semantic Layout Parsing) — in progress

Decision (confirmed with you): full build — fine-tune YOLOv8 on CGL-Dataset's
own annotation taxonomy rather than use generic pretrained COCO classes or a
lightweight heuristic-only remap.

**CGL-Dataset taxonomy** (enumerated directly from the dataset, not assumed):
exactly 4 categories — `logo` (id 1), `text` (id 2), `underlay` (id 3),
`embellishment` (id 4). Clean, well-defined, ideal for a 4-class detector.

**Mapping to ThemeSync's `structural_class`:** `text` → `text_node`;
`logo`/`underlay`/`embellishment` → `image_node` (the closest existing
category for a non-text graphic element — ThemeSync's schema is coarser than
CGL's). `repeating_group` (e.g. the 3 signature blocks in the certificate
domain) has **no YOLO-detectable equivalent** — it's a template-specific
structural pattern, not a generic visual category. Detected text boxes are
never auto-grouped into one; each becomes its own `text_node`. Flagged as a
known limitation, not silently handled.

**Data pitfall caught and fixed:** the first training attempt produced a
model with a perfectly normal, steadily decreasing training loss
(box/cls/dfl: 2.46/3.06/2.02 → 1.31/1.36/1.34 over 30 epochs) but exactly
`0/0/0/0` precision/recall/mAP on validation, every single epoch. Root
cause: I'd sourced the validation split from CGL-Dataset-v2's own `test`
split, assuming it had real annotations — direct inspection showed it
doesn't. Every `test`-split example carries a dummy placeholder annotation
(`bbox: [1, 2, 3, 4]`, `area: 12`) — CGL-Dataset-v2 evidently withholds real
test-set ground truth publicly (common for benchmark releases with a
held-out leaderboard). So every validation "match" was being scored against
meaningless placeholder boxes — the model may have been learning fine, the
*evaluation* was garbage. Fixed by sourcing both train and val from CGL's
real `train` split at disjoint index ranges (`train[0:3000]` /
`train[3000:3300]`) instead. Re-verified the corrected val labels have a
realistic 4-class distribution before retraining (previously: 100% class 0).
Flagging this because it's the kind of silent failure that's easy to miss —
a model can look like it "trained successfully" (clean loss curve, no
errors, weights file saved) while its reported metrics are meaningless.

**Built:**
- `src/data_preprocessing/prepare_yolo_dataset.py` — exports a subset of
  CGL-Dataset (reusing the same HF cache as GNN training) into YOLO's
  expected `images/`+`labels/`+`data.yaml` layout, converting `[x,y,w,h]`
  pixel annotations to YOLO's normalized `cx,cy,w,h` format. Ran with 3000
  train / 300 val samples (both from CGL's `train` split — see pitfall
  above) — 0 skipped (clean conversion).
- `src/models/train_yolo_extractor.py` — fine-tunes a pretrained `yolov8n.pt`
  base via the `ultralytics` API (already a pinned dependency —
  `requirements.txt` had it unused, now actually used). 30 epochs, imgsz 640.
- `src/data_preprocessing/layout_extractor.py` — inference wrapper:
  `LayoutExtractor.extract(image_path)` runs the fine-tuned detector, sorts
  detections into reading order (logo first, then top-to-bottom by y), maps
  each to a `structural_class`, and for `text_node` detections crops the
  region and runs Tesseract OCR (installed via conda-forge into
  `themesync_env` — wasn't present on the system at all until this session)
  to extract literal text (`node['ocr_text']`). Output is a node list with
  the same schema contract as `NodeInstantiator.instantiate_payload()`
  (`node_id`, `semantic_category`, `structural_class`, `spatial_hierarchy`,
  `bbox`, `constraint_type`), so it's a drop-in alternative input to the rest
  of the pipeline (GNN → CSP → AAPA), not a parallel schema.

**Training status:** complete (30 epochs, yolov8n base, 3000 train / 300 val,
correct — non-placeholder — validation split). Final validation:

|---|---|---|---|---|---|---|

Solid first-pass result for logo/text/underlay (the three classes that
actually matter for ThemeSync's structural_class mapping — see above).
**embellishment failed completely** — it's only 370 of ~15,000 training
instances (2.5%), too few for the model to learn it at all. Practical
impact is lower than it sounds: embellishments (decorative ribbons/stickers)
are the least structurally important element type for the certificate/ID
domain, and they still get correctly routed to `image_node` if detected —
they just mostly won't be detected. If this matters for your use case,
fixing it means oversampling embellishment examples during dataset export
(not attempted this pass — flagging rather than silently leaving it).

Weights saved to `themesync_yolo_v1.pt` (repo root, matching the
`themesync_gnn_v1.pth` / `themesync_cnn_v1.pth` convention).

**CRITICAL finding — domain mismatch on ThemeSync's actual target images.**
Ran `LayoutExtractor.extract()` against 3 real template images in
`data/raw/` (`sample_template.png`, `YOUR_TEMPLATE.png`, `YOUR_TEMPLATE2.jpg`).
At the default confidence threshold (0.25): **zero detections** on 2 of 3;
one weak logo detection (conf 0.46) on the third. Lowered the threshold to
0.01 to check whether the model was seeing *nothing* or just *not confident
enough* — it's the latter: `sample_template.png` produces 78 candidate boxes,
but the highest confidence among them is 0.11; `YOUR_TEMPLATE.png` produces
5 candidates topping out at 0.035. Both far below any usable threshold.

Root cause: this isn't a bug, it's a genuine train/inference domain gap. The
model generalizes fine *within* CGL-Dataset's own domain (mAP50=0.539 on its
own held-out images — real-world advertising/e-commerce posters: product
photography, dense marketing graphics). ThemeSync's actual target templates
(formal academic certificates, ID cards — sparse, mostly whitespace,
navy/gold institutional styling) are a visually different genre entirely.
This is the *same underlying issue* already flagged for the GNN back in
Part 1, finding 1.2/1.3 — CGL-Dataset is out-of-domain relative to
ThemeSync's actual use case — just now confirmed for YOLO too, and more
visibly, since detection confidence is a much more direct signal of "does
this model recognize what it's looking at" than a spatial-prediction loss
value is. Worth stating as one unified, cross-cutting limitation rather than
two separate ones: **both of ThemeSync's learned components share a training
corpus that doesn't represent its actual deployment domain.**

This means the "full build" as currently trained is **not yet usable on
ThemeSync's real templates** — it works, but only on CGL-Dataset's own kind
of imagery. Fixing this properly needs either (a) a small set of *real*
certificate/ID master templates, hand-annotated with logo/text/underlay
boxes, to fine-tune further on top of the CGL base (transfer learning from
a reasonable starting point, rather than from scratch), or (b) accepting
this as a documented limitation and future-work item alongside the GNN's
own domain-mismatch finding. Did not attempt (a) this session — no such
annotated set exists yet, and creating one is a data-collection task in its
own right, not a code fix.

**Integration (deliberately not done yet):** `layout_extractor.py` is
standalone, not wired into `pipeline.py`'s default flow. Whether it should
*replace* the JSON-schema-payload path or run *alongside* it (YOLO/OCR for
the master template's own structural analysis, schema payload still for
per-record dynamic content substitution) is an open design question — same
treatment as the CNN, kept out of scope until you decide.
